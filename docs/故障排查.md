## 生成阶段

### 生成器自检失败

**现象**

```
SELF-CHECK FAILED:
  - nested array detected at .route.rules[4].ip_cidr[0] — the sentinel must be the entire value, not an element of a list
```

或

```
  - contains refused key(s): listen, listen_port
```

**原因**

- 嵌套数组：CIDR 占位符被写成了数组元素。替换后会变成 `[[...]]`，引擎报
  `unknown format of a string list` 并拒绝启动。
- 被禁键：配置里出现了设备会剥离或会误解释的字段（`listen`、`redirect`、
  `override_address` 等）。

**怎么办**

不要手改生成器输出的那段 CIDR 块。如果确实需要自己拼配置，记住：占位符必须
**占用整个值**，而不是数组里的一个元素。

```jsonc
"ip": ["__MU300_CN_CIDRS__"]   // ✗ → [[...]]
"ip": "__MU300_CN_CIDRS__"     // ✓
```

### 没有读到 CN 段

**现象**：`error: no IPv4 ranges read from .../data/cn-ipv4.txt`

**怎么办**：`scripts/fetch-cn-cidrs.sh`。如果机器不能出网，从别的机器把这个文件
拷过来即可（格式是每行一个 CIDR）。

## 安装阶段

### `profile import` 被拒

**先看真实原因**，设备的报错是直接可读的：

```sh
mu300-vpn profile import out/split-cn.singbox.json probe 2>&1 | tail -3
```

常见原因：

| 报错关键词 | 原因 | 怎么办 |
|---|---|---|
| `top-level key` | 出现白名单外的顶层键 | 生成器只会输出 `dns` / `outbounds` / `route`；手改过就删掉多余的键 |
| `larger` / `1 MiB` | 文件超限 | 只可能发生在你手工内联了额外数据时 |
| `unknown format of a string list` | 嵌套数组 | 见上一节 |
| `not allowed` / `refus` | 含被禁键 | 删掉 `listen` / `redirect` / `override_address` 之类 |

> 判断"是否真的被拒"要用 `mu300-vpn check <ID>`（**顶层**子命令）。
> `mu300-vpn profile check <ID>` 会打印用法错误也返回非零——用它当判据会得到假阳性。

### `mu300-vpn check` 被拒

```
route.final=proxy is not a known outbound [direct]
```

或

```
rules[3].outbound=direct is not in outbounds [proxy]
```

**原因**：`route.rules[].outbound` 和 `route.final` 必须指向某个
`outbounds[].tag`。设备会逐条断言。

**怎么办**：检查 `outbounds` 里是否有 `tag: "direct"` 和 `tag: "proxy"`，
拼写（大小写）是否一致。

## 运行阶段

### 隧道起来了，但境外完全不通

按顺序排查：

```sh
# 1. 引擎在跑吗、TUN 在吗
ssh root@$DEV 'ps w | grep -E "[s]ing-box|[x]ray"; ip link show sbtun 2>/dev/null'

# 2. 隧道本身通不通（看引擎日志）
ssh root@$DEV 'logread | grep -iE "sing-box|vless|outbound" | tail -20'

# 3. 服务器能连吗
ssh root@$DEV 'ping -c3 -W3 <服务器IP>'
```

**最可能的原因：`outbounds` 里的节点参数不对。**

这是**千万不要手抄参数**的理由——Reality 公钥少一个字符、`flow` 没写、
`server_name` 与服务器不符，都会表现为"超时"，没有任何指向性错误信息。

**怎么办**：回到 `--base` 模式，让设备自己生成 `outbounds`：

```sh
ssh root@$DEV 'MU300_VPN_RUN=/tmp/gen mu300-vpn gen >/dev/null 2>&1; cat /tmp/gen/config.json' > device-base.json
python3 scripts/gen-split-config.py --base device-base.json
```

### 境内也走 VPN 了

**先确认判据**：不要用"打开百度很快"来判断，用出口 IP。

```sh
scripts/verify.sh --host $DEV
```

**原因与处理**：

| 可能 | 检查 | 处理 |
|---|---|---|
| CN 规则没进去 | `tools/verify-routing.py out/…singbox.json` 里 `direct tags` 数量 | 应为 7456；为 0 说明生成时 CN 段没读到 |
| 规则被 rebuild 丢了 | `sandbox-test.sh` 的 `CN range list survived the rebuild` | 若失败，说明用了 `uri` 形态的 profile 而不是 `config.json` |
| 目标不在 CN 段内 | `python3 -c "import ipaddress; …"` | 见下一节 |
| 该 IP 的域名先解析成了境外 IP | 见下一节 | 见下一节 |

**最常见的是最后一条**——判据是**目标 IP**，而域名要先解析出 IP 才能判。

### 国内站点被判成境外

**现象**：访问某个国内站点，出口 IP 是 VPN 服务器。

**原因**：设备与 LAN 的 DNS 被 `hijack-dns` 拉进隧道，从隧道出口解析。国内 CDN
会按解析来源做就近调度，少数情况下返回境外节点 IP，于是被判成"非中国大陆"。

**验证**

```sh
python3 - <<'PY'
import ipaddress
nets=[ipaddress.ip_network(l.strip(),strict=False) for l in open('data/cn-ipv4.txt') if l.strip()]
ip=ipaddress.ip_address("在这里填解析出来的 IP")
print("在 CN 段内" if any(ip in n for n in nets) else "不在 CN 段 → 会被判成境外")
PY
```

**处理**（两条路，按可接受程度排序）

1. **换隧道内的解析器**：把 `dns.servers` 里 `remote` 那条的 `server` 改成国内 DNS
   （例如 `223.5.5.5`）。代价是解析请求会从隧道出去、到国内 DNS 解析，但结果更贴近
   国内视角。
2. **加域名直连规则**：在 CN 规则**之前**插入
   `{ "domain_suffix": [".example.cn"], "outbound": "direct" }`。
   注意：**只在 sing-box 路径下有意义**（它开了 sniffing）；Xray 路径看不到域名，
   写了也是死代码。

### 分流没生效：境内境外出口 IP 相同

**先确认两个出口应该不同**：

```sh
scripts/verify.sh --host $DEV
```

若两者相同，说明所有流量走了同一条路。逐项排查：

| 检查 | 期望 |
|---|---|
| `mu300-vpn status` 的 `profile` | 是 `split-cn`（sing-box），不是原来的分享链接 profile |
| `active` 文件 | `cat /etc/mu300/vpn/active` 是 `split-cn` |
| 设备上实际运行的配置 | `cat /run/mu300-vpn/config.json \| jq '.route.rules \| length'` 应 ≥ 5 |
| CN 规则在不在 | `jq '.route.rules[-1].ip_cidr \| length' /run/mu300-vpn/config.json` 应约 7456 |

**如果 `/run/mu300-vpn/config.json` 里没有 CN 规则**，说明设备加载的不是你的配置。
最常见原因是 profile 用的是 `uri` 形态（路由写死）而不是 `config.json` 形态。
用 `sandbox-test.sh` 可以提前发现这一点。

### IPv6 泄漏

```sh
scripts/verify.sh --host $DEV        # 默认包含 IPv6 探针
```

期望：**所有 IPv6 探针失败**。

设备侧应当有：

```sh
ssh root@$DEV 'ip -6 rule show | head -3'
# 9000:   from all unreachable
```

⚠️ **不要用 `exec 3<>/dev/tcp/8.8.8.8/53` 判断泄漏。** 对走 TUN 的目标，
sing-box 的 gvisor 栈会在**本地完成三次握手**，看起来"连上了"，实际什么都没出去。
判泄漏只看出口 IP 和 IPv6 探针。

### 隧道被自动关闭（`ENABLE` 变 0，kill switch 被撤）

**现象**

```sh
cat /etc/mu300/vpn.conf      # ENABLE=0
nft list tables              # 没有 table inet mu300_vpn
ls /etc/rc.d/ | grep vpn     # 符号链接消失
```

**含义**：`mu300-vpn off` 被执行过（`off` 分支里的 `svc disable` 删掉了 rc.d 链接）。
这段时间 LAN 流量是**明文直出**的。

**排查**

```sh
ssh root@$DEV '
  echo "-- 有无 dropbear 会话（有没有人 SSH 进来过）--"; logread | grep dropbear | tail -5
  echo "-- mu300-power 状态目录（不存在 = 其 VPN 逻辑未触发）--"; ls -d /run/mu300-power 2>/dev/null
  echo "-- 谁调用了 off --"; grep -rn "mu300-vpn off" /opt/mu300/bin /etc/init.d /etc/hotplug.d 2>/dev/null
  echo "-- Web 面板 --"; netstat -ltnp 2>/dev/null | grep -E ":80|:443"
'
```

**已确认的事实**

| 组件 | 行为 |
|---|---|
| `/etc/init.d/mu300-vpn stop` | **不撤** kill switch（设计如此：崩溃不泄漏）；且 `respawn` 约 5 秒后拉起服务 |
| `mu300-power` | 只在 modem 掉线时做 service stop，**不写 `ENABLE`** |
| 设备脚本 | `set_enable 0` 的唯一调用点是 `mu300-vpn` 的 `off)` 分支，没有脚本调用它 |
| Web 面板（`uhttpd` 监听 80/443） | 可经 ubus/CGI 调用 `mu300-vpn`，是剩下唯一的入口 |

**建议**：把面板关掉或改端口，观察是否复现。若在隧道持续异常时复现，那是组件在
隧道不健康时主动关闭 VPN —— 这与它"fail closed"的设计意图相悖，值得向 mu300-linux
项目反馈。

**恢复**：

```sh
ssh root@$DEV 'mu300-vpn on && mu300-vpn status'
```

### 部署后 SSH 连不上设备

**不用慌。** kill switch 只作用于 `sipa_eth*` 与 `wlan0` 的**出方向**，SSH 走
`br-lan`，不受影响。真正的风险只有一处：`deploy.sh` 里的 `mu300-vpn off` 会撤掉
kill switch（但同样不影响 LAN 侧 SSH）。

如果确实连不上：

1. 从**同一 LAN** 的机器 ping 设备地址；
2. 检查是不是把 `LAN_CIDRS` 设置成了不包含你客户端的网段——这会让 LAN 流量被
   `reject` 规则挡住（不过 TUN 的 `route_exclude_address` 会先让 LAN 不进隧道，
   所以通常不至于）；
3. 最坏情况用串口/恢复模式，从步骤 1 的备份还原。

**预防**：`deploy.sh` 第 2 步设置的 `LAN_CIDRS` 必须与客户端实际网段一致。

## 观测与测量

### `nft list ruleset` 两次输出不同

`counter packets` 计数在变。比对前后状态前过滤掉：

```sh
nft list ruleset | grep -v 'counter packets'
```

### 设备上没有 `tcpdump`、没有 `curl`

只有 busybox `wget`。用它做测试：

```sh
# 出口 IP
wget -4 -qO- -T 15 http://ifconfig.me/ip

# 国内回显
wget -4 -qO- -T 15 http://ip.3322.net
```

注意：busybox `nc` **不支持 `-w`**（`nc [IPADDR PORT]` 才是合法形式），
用它做连通性断言会得到假"不通"。

### 想验证某一台主机走哪条路

按 IP 精确测试，绕开 DNS：

```sh
curl -4 -s --resolve ifconfig.me:80:198.51.100.7 http://ifconfig.me/ip
curl -4 -s --resolve ip.3322.net:80:118.184.169.32 http://ip.3322.net/
```

前者应返回 VPN 出口，后者应返回运营商出口。

### 想知道某个 IP 在不在 CN 段内

```sh
python3 - <<'PY'
import ipaddress
nets=[ipaddress.ip_network(l.strip(),strict=False) for l in open('data/cn-ipv4.txt') if l.strip()]
ip=ipaddress.ip_address("8.8.8.8")
hit=[str(n) for n in nets if ip in n]
print(hit or "不在 CN 段内")
PY
```

## 性能

### 境内访问也慢

**现象**：境内站点耗时和境外差不多（都是秒级）。

**含义**：境内流量绕道境外了。用出口 IP 确认（见上）。

**如果出口 IP 正确但仍然慢**：可能是 `route.rules` 的匹配开销。
7456 条 CIDR 是线性扫描，但 sing-box 内部会对规则集做优化；实测境内 ~0.09 s、
境外 ~1.0 s，差值约等于隧道 RTT，是正常量级。

## 还没解决？

收集这几样东西，问题基本就定位了：

```sh
# 设备侧
ssh root@$DEV '
  mu300-vpn status
  mu300-vpn settings get
  mu300-vpn profile list
  echo "-- 规则表 --"; jq ".route.rules | map(if .ip_cidr then . + {ip_cidr: (.ip_cidr|length)} else . end)" /run/mu300-vpn/config.json
  echo "-- 内核 --"; ip rule show; ip route show table 2022 | head
  nft list tables
  echo "-- 日志 --"; logread | grep -iE "sing-box|vpn" | tail -30
'
```

以及本地的：

```sh
python3 tools/verify-routing.py out/split-cn.singbox.json
scripts/sandbox-test.sh --host $DEV --config out/split-cn.singbox.json --keep
```

**凭据脱敏**：贴日志之前把服务器 IP、UUID、Reality 公钥替换掉。
