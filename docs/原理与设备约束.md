# 原理与设备约束

[← 返回 README](../README.md) · [English](how-it-works.md)

这份文档解释**为什么**这套工具必须长成这样。每一条结论都来自对设备上真实脚本与二进制的检查与实测（`bin/mu300-vpn`、`lib/vpn/*.sh`、`xray`、`sing-box`），不是从上游文档推断的。

---

## 一、mu300-vpn 的设计意图

`mu300-vpn` 是一个**故障关闭（fail closed）**的全隧道组件，它的设计目标很明确：

1. 把设备自身与 LAN 的全部出向流量都送进隧道；
2. 用一个 kill switch 保证**隧道断了就丢包**，绝不回落到明文直出。

整套设计里没有"分流"这个概念。它甚至专门做了保证：**服务被停掉时 kill switch 依然生效**，所以进程崩溃不会导致流量泄漏。

这意味着分流不是"改个开关"，而是要在这个框架里找到一个能被引擎接受的注入口。

## 二、两条引擎路径

设备上有两套引擎，各有各的驱动方式：

| | Xray 路径 | sing-box 路径 |
|---|---|---|
| 触发条件 | `KILL_SWITCH=0` 时的分享链接 profile | `KILL_SWITCH=1`（默认），或 raw config profile |
| 引擎 | `xray` + `hev-socks5-tunnel` | `sing-box` |
| 路由来源 | `DRV_ROUTES=core`：内核 `ip rule` + `table 2022` 把全部流量送进 `xtun` | `DRV_ROUTES=self`：sing-box 的 `auto_route` 自己装规则 + 自己的 TUN `sbtun` |
| 入站 | 回环 SOCKS，`hev-socks5-tunnel` 把 IP 层包翻译成 SOCKS | TUN（gvisor 栈，`172.19.0.1/30`） |
| 有没有 sniffing | **没有** | 有（规则里显式写 `action: sniff`） |

### 2.1 引擎会被人为切换

`pick_engines` 里有一行：

```sh
if [ "$ENGINE" = xray ] && [ "$KILL_SWITCH" = 1 ] && [ -x "$BIN" ]; then ENGINE=sing-box; fi
```

也就是说：**默认设置下，只要装了 sing-box，引擎一定是 sing-box。** 你写的 Xray 配置不会被加载——不是"没生效"，是"根本没读"。

实测佐证：设备上 `/run/mu300-vpn/iface` 残留内容是 `sbtun`。

### 2.2 后果

| 做法 | 结果 |
|---|---|
| 用分享链接 profile，指望在配置里加规则 | `gen_singbox()` 的路由是**代码写死**的，你没有插手的位置 |
| 写一份 Xray 原生 JSON | 默认 `KILL_SWITCH=1` 下**永远不会被加载** |

## 三、profile 的两种形态

sing-box 驱动接受两种 profile：

| profile 文件 | 生成函数 | 路由规则从哪来 |
|---|---|---|
| `$PDIR/uri`（分享链接） | `gen_singbox()` | **代码写死**：`sniff → hijack-dns → LAN+私网 reject → 私网 direct`，`final: proxy`。**没有任何大陆直连规则** |
| `$PDIR/config.json`（raw 配置） | `gen_singbox_json()` → `singbox_json_rebuild()` | **保留配置自己的 `route.rules`**，只做覆盖 |

这就是唯一的注入口：**raw config 形态**。

### 3.1 rebuild 阶段做了什么

`singbox_json_rebuild()` 的覆盖行为：

**保留的顶层键**：`dns`、`outbounds`、`route`、`endpoints`
（`log`、`inbounds`、`experimental` 等被丢弃或替换）

**`route` 下保留的键**：`rules`、`rule_set`、`final`、`default_domain_resolver`
保留键之外的一律丢弃。

**强制覆盖**：

```jsonc
"inbounds": [{                       // 完全替换成设备自己的 TUN
  "type": "tun", "tag": "tun-in", "stack": "gvisor",
  "interface_name": "sbtun", "address": ["172.19.0.1/30"], "mtu": 1400,
  "auto_route": true, "strict_route": true,
  "route_exclude_address": ["<LAN_CIDRS>"]
}],
"route": {
  "default_mark": 720,               // = 0x2d0，kill switch 唯一放行的标记
  "auto_detect_interface": true,
  "default_domain_resolver": "bootstrap"
},
"dns": { "servers": [ /* … , */ {"type":"udp","tag":"mu300-bootstrap","server":"…"} ] }
```

**断言**：每条 `route.rules[].outbound` 与 `route.final` 必须指向某个 `outbounds[].tag`，否则拒收。

### 3.2 由此得到的实现约束

- 规则表必须由我们**写全**。设备的模板规则（sniff / hijack-dns / 私网 reject）在 raw config 路径下**不会**被自动补上。
- `outbounds` 里的代理参数必须与设备预期一致，否则隧道连不通——而设备覆盖 `inbounds` 却不覆盖 `outbounds`，所以错一点就直接坏。
- 这就是推荐 `--base` 模式的理由：**让设备自己生成 `outbounds`，你只追加规则。**

## 四、约束逐条

### 4.1 引擎看不到域名

Xray 驱动的入站是回环 SOCKS 且没有 `sniffing`：

```jsonc
"inbounds": [{ "protocol": "socks", "listen": "127.0.0.1", "port": 10808 }]
```

`hev-socks5-tunnel` 只把 IP 层包翻译成 SOCKS 连接。从头到尾**没有任何环节解析出域名**。

**结论**：`domain:` 规则在本设备上是死代码。判据只能是 IP 段。

### 4.2 `geoip:cn` 不可用

镜像里没有 `geoip.dat` / `geosite.dat`。写了 `geoip:cn` 的配置在 `xray -test` 阶段直接报错退出。

**结论**：7456 条大陆段必须**内联**进 JSON。

### 4.3 1 MiB 上限

profile 文件超过 1 MiB 会被拒收。内联 7456 条 IPv4（+ 可选 3473 条 IPv6）后约 141 KB，余量充足。

### 4.4 直连出口必须带 mark

设备只在**已经是对象**的 `streamSettings` 上写 `sockopt.mark=720`：

```sh
# 伪码
if (.streamSettings | type) == "object" then
    .streamSettings.sockopt.mark = 720
end
```

所以直连出口如果省掉 `streamSettings`，它就拿不到 mark，包会被 kill switch 丢掉。

> **"直连"没有 mark 就不是直连，是黑洞。**

工具生成的直连出口因此长这样（`streamSettings` 即使是空对象也必须存在）：

```jsonc
{ "tag": "direct", "protocol": "freedom",
  "settings": { "domainStrategy": "UseIP" }, "streamSettings": {} }
```

### 4.5 CIDR 哨兵必须是"整个值"

工具内部用 `__MU300_CN_CIDRS__` 占位，渲染时替换成整齐的多行 CIDR 块。如果写成数组元素：

```jsonc
"ip": ["__MU300_CN_CIDRS__"]      // ✗ 替换后变成 [[...]]
```

替换带引号的哨兵后会得到**嵌套数组**，引擎直接报：

```
unknown format of a string list: [[ "0.0.0.0/8", ...
```

正确写法是让哨兵占用整个值：

```jsonc
"ip": "__MU300_CN_CIDRS__"        // ✓
```

生成器在渲染后做了两道自检：重新 `json.loads()`，并遍历确认**没有任何数组里还套着数组**。

### 4.6 `check` 是顶层子命令

```
mu300-vpn check <ID>
```

不是 `mu300-vpn profile check <ID>`。写成后者会打印用法错误并以非零退出——如果你用它当"负样本被拒绝"的判据，会得到**假阳性**（脚本以为"被拒了"，其实是命令用错了）。

### 4.7 其它实测细节

| 现象 | 说明 |
|---|---|
| `nft list ruleset` 两次输出不同 | `counter packets` 计数在动。比对前先 `grep -v 'counter packets'` |
| busybox `nc` 不支持 `-w` | `nc [IPADDR PORT]` 才是合法形式。用它做连通性断言会得到假"不通" |
| `exec 3<>/dev/tcp/8.8.8.8/53` 会"连上" | 走 TUN 的目标由 **sing-box 的 gvisor 栈在本地完成握手**。不能用来判泄漏 |
| 设备上没有 `tcpdump`、没有 `curl` | 只有 busybox `wget`（不支持 `-4`，靠 DNS 返回 IPv4） |
| `/etc/init.d/mu300-vpn stop` 摁不住 | `procd_set_param respawn 3600 5 0`，约 5 秒后自动拉起。要真停用 `mu300-vpn off`（但那会撤掉 kill switch） |
| 服务 stop 不撤 kill switch | 符合设计注释：崩溃不泄漏 |
| `mu300-power` 会在 modem 掉线时 `vpn_stop` | 但它只做 service stop，**不写 `ENABLE`**；且其状态目录不存在时说明该逻辑未触发 |

## 五、运行期的内核结构

分流决策发生在**用户态**（sing-box 内部），内核只负责让流量进出 TUN 和让引擎自己的连接绕过 TUN。

```
ip rule
  5198:  fwmark 0x2d0 lookup main          ← 引擎自己的包（带 mark）走主表 → 蜂窝口直出
  9000:  to 172.19.0.0/30 lookup 2022      ← 目的在 TUN 网段
  9001:  lookup 2022 suppress_prefixlength 0
  9002:  dns → main / iif sbtun goto 9010
  9003:  iif lo → 2022
  9010:  nop

table 2022: 0.0.0.0/1、128.0.0.0/2 … 全部 via 172.19.0.2 dev sbtun
            192.168.77.0/24 被排除

nft table inet mu300_vpn        ← kill switch
  chain output/forward: oifname "sipa_eth*" meta mark 0x2d0 accept
                        其余 drop

ip -6 rule
  9000: from all unreachable    ← IPv6 封闭（sing-box 所装）
```

关键点：**引擎自己的连接是靠 `mark 0x2d0` 绕过 TUN 的**，不是靠 `route.rules`。所以：

- 即使 VPN 服务器地址不落在任何 `direct` 规则里（通常如此），也不会形成环路；
- 反过来，`route.rules` 只作用于**从 TUN 进来**的流量。

## 六、完整数据流

以一次 LAN 客户端访问 `www.example.cn` 和 `www.example.com` 为例：

```
① DNS
   客户端 → 设备 DNS → 规则 ② hijack-dns → 隧道内解析器
   （所以解析结果带有隧道出口的视角，见故障排查）

② 境内目标 223.0.103.X（假设在大陆段内）
   LAN 包 → br-lan → [不在 route_exclude_address? 是则在 LAN]
          → TUN sbtun → sing-box route.rules
             ④ 私网？否
             ⑤ 在大陆 7456 段内？是 → outbound: direct
          → sing-box 用 direct 出口自连，socket 带 mark 720
          → 内核规则 5198 → main 表 → sipa_eth0 → 蜂窝直出
   出口 IP = 运营商 IP

③ 境外目标 198.51.100.x
   LAN 包 → TUN sbtun → route.rules
             ④ 私网？否   ⑤ 大陆段？否
          → final: proxy
          → VLESS 隧道 → VPN 服务器
   出口 IP = VPN 服务器 IP
```

两个出口**非此即彼**，这就是 `scripts/verify.sh` 的判据基础。

## 七、为什么不能简化

一个自然的想法是："既然 sing-box 有 `auto_route`，为什么不直接把 CN 段写进 `route.rules` 交给它？"

可以，但这正是本工具在做的事——难点全在**参数**上：

- `outbounds` 里 Reality 的公钥、`short_id`、`server_name`、`flow`、`packet_encoding`、`utls.fingerprint` 有一处不对，隧道就连不通，而错误信息往往是"超时"，毫无指向性；
- `dns` 块的 `type: tcp` + `detour: proxy` + `final: remote` + `strategy: ipv4_only` 组合是设备生成的形态，不是随便写的；
- `domain_resolver: bootstrap` 依赖第二个 DNS server 的 `tag`，改名字就断链。

所以最省事的做法反而是**先让设备生成，再只改规则**。这也是 `--base` 模式存在的唯一理由。
